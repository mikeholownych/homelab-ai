# Model evaluation for llama.cpp workers: final report (2026-10-07)

**Scope:** model selection for the two llama.cpp pools on ai-5820-01 (2x Arc Pro B65 32 GB, llama.cpp `5fc4f3c8c`, pinned prod
image); the effect of reasoning mode; and the unbounded-reasoning defect.

**Status:** evaluation complete. Production is restored with its original configuration (both workers healthy via the gateway at
12:21Z). **No production change has been made. Everything under "Recommendations" needs separate authorization.**

**Evidence:**
- `ai-5820-01:~/engx/`: `results/` (instrumented runs), `evidence/UNBOUNDED_REASONING/`, `evidence/PILOT/`,
  `logs/invalid/`, `evidence/engx-report-2026-10-07.md` (per-attempt tables).
- Local copy of the per-attempt tables: `results-2026-10-07-report.md`.

## 1. Method
- **Corpus:** engx hard corpus H01-H10 (spec implementation, multi-bug repair, migration, performance, root cause), hidden-test
  validators in bwrap; up to 3 attempts per task with CI-style feedback; 3 reps; temperature 0. Same corpus digest for every run.
- **Serving:** one candidate per GPU, prod image digest, prod flags (`-ngl 99 --jinja -np 1 -fa on -b 4096 -ub 2048`), direct to
  the worker. This was an operator-approved one-off exception to the gateway-only / remote-origin policies.
- **Conditions (never pooled):**

  | Condition | Settings |
  |---|---|
  | THINKING_OFF | client `enable_thinking=false`, max_tokens 4096 |
  | THINKING_ON_UNBOUNDED | template default thinking, max_tokens 16384, server `--reasoning-budget -1` (the prod default) |
  | THINKING_ON_BOUNDED_4096 | as UNBOUNDED, plus `--reasoning-budget 4096 --reasoning-budget-message "Reasoning budget exhausted. Stop reasoning now and write the final answer in the required format."` This is the only change from UNBOUNDED. |

- **Bounded-mechanism validation:** reasoning was cut at 4096 (+18 tokens of injected message, i.e. 4114), the message is present
  in `reasoning_content`, and a final answer followed. Budget detection uses an exact token count from the engine's `/tokenize`
  OR message presence.
- **Failure classes (per attempt; a task-run is classed by its final attempt):**
  - MODEL_CAPABILITY: a valid final answer was rejected by the validators, or the model stopped normally without a usable answer.
  - REASONING_BUDGET_EXHAUSTION: bounded condition, budget reached, no valid answer.
  - SERVING_CONFIGURATION_FAILURE: cut by an output/context ceiling before a valid answer, or a request error.
- **Not measured, a limitation:**
  - Long-context load. Prompts are short (about 0.5-6K tokens), so the 64K window was configured but never filled.
  - Tool calling and multi-turn agentic use (Nexus's real workload).
  - The gateway path.
  - Statistical independence of reps. At temperature 0 reps are near-deterministic, so the effective sample is closer to 10 tasks
    than 30 runs. Differences of 1-2 tasks between models are NOT reliable.

## 3. What the results mean

1. **The current lead model is the weakest link.** Qwen3-Coder-30B solves 10% of the hard corpus, while every 2026 candidate solves
   70-90%. This is the largest and most reliable effect in the evaluation (far beyond the sample-size caveat).
2. **Reasoning helps only when it is bounded.** Unbounded reasoning turned Qwen3.5 from 70% into 53% and Flash-Next from 80% into
   about 6%, through SERVING_CONFIGURATION_FAILURE. Bounded at 4096:
   - it recovers Qwen3.5 to its thinking-off level;
   - it lifts Qwen3.8 (+13 pts), Qwen3.6 (+10) and Flash-Next (+10).
   The production deep route currently runs the harmful configuration (see the defect).
3. **4096 is binding and is not an optimum.** Qwen3.8, Qwen3.6 and Flash-Next hit the budget on about 100% of attempts, so their
   reasoning distribution is censored and this data cannot show the best budget. Qwen3.5 (median 2510) mostly finishes within it.
   **Additional budget points are required** before choosing a production value (section 6).
4. **Top tier (statistically indistinguishable here): Flash-Next 90%, Qwen3.8 86.7%, Qwen3.6 80%.** They differ in cost:
   - Qwen3.6 decodes about 3x faster (58.6 tok/s; 87 s/attempt).
   - Flash-Next and Qwen3.8 take 260-390 s per attempt.
   - Flash-Next and Qwen3.8 are complementary: between them they solve all ten tasks.
5. **Model behaviour is not uniform, and the serving layer has to own it (layer principle):**
   - Glimmer reasons even when told not to, and `--reasoning off` does not stop it.
   - GLM ignores the fenced-output convention.
   - Thinking defaults differ by template.
   These are capabilities to *verify and report*, not assume.

## 4. Recommendations (NOT authorized; each needs operator approval)
1. **Deep-route defect, first:** apply a worker-side reasoning budget on the deep worker as the fail-safe. Choose the value from the
   budget sweep (section 6), not 4096 by default. Details are in the defect record.
2. **Lead pool:** replace Qwen3-Coder-30B with **Qwen3.6-35B-A3B**: 70% thinking-off / 80% bounded vs 10%, at the highest decode
   speed of any candidate.
3. **Deep pool:** **Flash-Next GSQ-RCO Coder** or **Qwen3.8-27B** with a bounded reasoning budget. Flash-Next is the slight leader
   but has open risks (section 6); Qwen3.8 is the lower-risk alternative (standard GGUF, 16.5 GB, no mmap'd side table).
   Decide after the qualification items in section 6.
4. **Keep the two-pool layout.** The merged-pool option (unpruned Flash-Next across both GPUs) is not justified: the pruned Coder
   already reaches 90% on one card.

- **Muse Glimmer 30B:**
  - Thinking-off run aborted: the model reasons regardless of the client flag and hits the output limit.
  - Server `--reasoning off` verified ineffective: the pilot recorded 4093 and 2749 reasoning tokens with the flag confirmed in
    the launch command, and the template has no thinking switch.
  - No valid thinking-off condition exists for it on this stack. Running Glimmer under BOUNDED_4096 would deviate from the approved
    experiment and is left to the operator.
- **GLM-4.7-Flash first run (0%):** a parser artifact (unfenced FILE blocks), preserved in `logs/invalid/`. After the parser fix:
  3.3%, with genuine failures including degenerate repetition loops.
- **Harness/runner defects found and fixed during the evaluation:**
  - podman cwd under PrivateTmp; journald log driver; fail-fast load;
  - parser fallback for unfenced FILE blocks;
  - per-attempt instrumentation and partial writes.
  None changed tasks, validators or scoring.

## 6. Additional work made apparent by the results
1. **Reasoning-budget sweep (required before choosing a value):** 2048 and 8192 (12288 if 8192 is still binding) for the top
   three plus Qwen3.5, with identical controls. Output: an acceptance vs budget vs latency curve per model.
2. **Long-context qualification:** fill 32-60K contexts (real Nexus transcripts) for each candidate.
   - It is mandatory for Flash-Next: llama.cpp could not verify its 64K memory fit ("failed to fit params to free device memory").
   - Measure OOM/errors, TTFT and decode at depth.
3. **Tool-calling / agentic qualification:** engx tests single-shot file output only, while Nexus drives tool calls over many turns.
   Replay recorded Nexus sessions or run a tool-call corpus through each candidate.
4. **Flash-Next operational risk:** its 28.8 GB n-gram table is mmap'd and depends on host page cache (61 GiB RAM).
   - Under memory pressure it degrades to disk reads.
   - Needs page-cache residency and major-fault monitoring before promotion.
   - Two Flash-Next instances would share one cached copy (same file), which opens a "Flash-Next on both cards" option for later.
5. **Re-qualification through the gateway, from a remote client:** required by the gateway-only / remote-origin policies before any
   promotion. Depends on the candidate alias pool (R4).
6. **Capability reporting gets concrete fields:**
   - `reasoning_controllable` (verified per model: Qwen yes, Glimmer no);
   - `reasoning_budget` (worker);
   - `output_contract_compliance` (verified).
7. **Glimmer decision (operator):** run it under BOUNDED_4096, or drop it. Recommendation: drop. Its aborted run was weak (2/17), it
   cannot be made to stop reasoning, and three stronger candidates exist.

## 7. Defect remediation: enforcement-boundary evaluation (unbounded reasoning, deep route)
Evaluated against the evidence above and the layer principle (each layer owns what it controls):

| Boundary | Role | Assessment |
|---|---|---|
| 1. Worker-side hard budget (`--reasoning-budget N` + message) | **Final fail-safe; mandatory.** | Validated here: cut exact at N, message injected, the answer follows, no SCF. Owned by the worker config (inventory), so it applies to every client including ones that send nothing. A per-model value is needed because the models use reasoning differently. |
| 2. Route/profile reasoning policy chosen by the client | **Selection, not enforcement.** | Nexus (the client) owns intent, e.g. a `reasoning=deep\|standard\|off` profile header. The gateway maps it to a budget at or below the worker cap. Whether llama.cpp accepts a per-request budget below the server cap must be verified before relying on it; if not, profiles map to separate worker configs. The client can never raise the worker cap. |
| 3. Gateway total-generation bound | **Mandatory.** | The gateway applies a default `max_tokens` when the client omits it (today it does not: runtime.py:499), sized from the worker's live limits as reasoning budget + answer allowance, within remaining context. Closes the "omit max_tokens" path at the gateway even if a worker is misconfigured. |
| 4. Telemetry | **Mandatory.** | The gateway classifies each completion as `reasoning_budget_exhausted` (injected message present in `reasoning_content`, or reasoning tokens at the cap), `output_limit` (finish=length), timeout, upstream error, or normal stop. It exposes these as distinct metrics and evidence fields, so budget exhaustion is never confused with model failure or a timeout. |

**Fail-closed:** layers 1 and 3 together guarantee that no request can obtain unlimited reasoning or unbounded generation by
omitting controls. Layer 2 can only lower limits. Layer 4 makes every exhaustion visible.
